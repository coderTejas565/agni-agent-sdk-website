# Runner

The `Runner` executes an `Agent` and manages its runtime lifecycle.

It is responsible for:

- Creating the execution context
- Registering agent tools
- Sending requests to model providers
- Executing requested tools
- Managing execution turns
- Publishing runtime events
- Returning normalized run results
- Streaming model output

An `Agent` defines **what an agent is**.

The `Runner` defines **how the agent runs**.

---

## Import

```ts
import { Runner } from 'agni-agent-sdk';
````

---

## Creating a Runner

Create a Runner without any configuration:

```ts
const runner = new Runner();
```

The Runner creates an `EventBus` internally.

You can also provide a custom event bus:

```ts
const runner = new Runner(customEventBus);
```

---

## Constructor

```ts
new Runner(eventBus?)
```

### Parameters

| Parameter  | Type       | Required | Description                              |
| ---------- | ---------- | -------- | ---------------------------------------- |
| `eventBus` | `EventBus` | No       | Custom event bus used for runtime events |

If no event bus is provided, Agni creates one automatically.

# `run()`

Executes an Agent and waits for the final result.

```ts
const result = await runner.run(
  agent,
  input,
  {
    context: {},
  },
);
```

---

## Signature

```ts
run<TOutput = string>(
  agent: Agent,
  input: string,
  options: RunOptions<TContext>,
): Promise<RunResult<TOutput>>;
```

---

## Parameters

| Parameter | Type                   | Required | Description                    |
| --------- | ---------------------- | -------- | ------------------------------ |
| `agent`   | `Agent`                | Yes      | Agent instance to execute      |
| `input`   | `string`               | Yes      | User input passed to the agent |
| `options` | `RunOptions<TContext>` | Yes      | Runtime execution options      |

---

# Run Options

```ts
interface RunOptions<TContext = unknown> {
  context: TContext;
}
```

The context object is available throughout the execution lifecycle.

Tools receive the current `RunContext` and can access the application context through it.

Example:

```ts
const result = await runner.run(
  agent,
  'Get my current weather.',
  {
    context: {
      userId: 'user_123',
    },
  },
);
```

---

# Returns

`run()` returns:

```ts
Promise<RunResult<TOutput>>;
```

The result is a discriminated union:

```ts
type RunResult<TOutput = string> =
  | RunSuccess<TOutput>
  | RunFailure;
```

Successful executions contain `output`.

Failed executions contain a structured `error`.

Example:

```ts
const result = await runner.run(
  agent,
  'Explain AI agents.',
  {
    context: {},
  },
);

if (result.success) {
  console.log(result.output);
} else {
  console.error(result.error.code);
  console.error(result.error.message);
}
```

See [`RunResult`](/docs/api-reference/run-result) for the complete result structure.

---

# Execution lifecycle

When `run()` is called, Agni creates a `RunContext` and enters the agent execution loop.

The high-level flow is:

```text
Agent
  |
  v
RunContext
  |
  v
Register Tools
  |
  v
Provider Request
  |
  v
Provider Response
  |
  +-------------------+
  |                   |
  | Text              | Tool Call
  |                   |
  v                   v
Final Output       ToolExecutor
                        |
                        v
                    Tool Result
                        |
                        v
                     Provider
                        |
                        v
                  Final Output
                        |
                        v
                    RunResult
```

The Runner continues the loop until:

1. The provider returns a final text response.
2. A tool execution fails.
3. A provider error occurs.
4. A runtime limit is exceeded.

---

# Execution turns

Each iteration of the agent loop is a runtime turn.

At the beginning of each turn, the Runner increments the turn counter.

```ts
context.incrementTurn();
```

The Runner also publishes a `turn.started` event.

The number of completed execution turns is available through:

```ts
result.metadata?.turns;
```

---

# Tool execution

When a provider requests a tool call, the Runner passes the request to `ToolExecutor`.

The flow is:

```text
User Input
    |
    v
Runner
    |
    v
Provider
    |
    v
Tool Call
    |
    v
ToolExecutor
    |
    v
Tool Result
    |
    v
Provider
    |
    v
Final Response
```

The Runner:

1. Receives the tool call from the provider.
2. Resolves the tool through `ToolRegistry`.
3. Executes the tool through `ToolExecutor`.
4. Adds the tool result to the conversation.
5. Sends the updated conversation back to the provider.
6. Continues the execution loop.

Example conversation state:

```text
User
  |
  v
Provider
  |
  v
Tool Call
  |
  v
Tool Execution
  |
  v
Tool Result
  |
  v
Provider
  |
  v
Final Response
```

---

# Tool failures

Tool failures are returned as structured runtime failures.

Depending on the tool system, errors can include codes such as:

* `TOOL_NOT_FOUND`
* `TOOL_EXECUTION_ERROR`
* `TOOL_VALIDATION_ERROR`
* `TOOL_REGISTRATION_ERROR`

Example:

```ts
const result = await runner.run(
  agent,
  'Get the weather.',
  {
    context: {},
  },
);

if (!result.success) {
  console.error(result.error.code);
}
```

Use `error.code` for programmatic error handling rather than parsing error messages.

See [`Error`](/docs/api-reference/error) for the error system.

---

# Provider errors

Provider failures are normalized before being returned through `RunResult`.

The Runner converts unknown provider failures into `ProviderError` when necessary.

Example:

```ts
const result = await runner.run(
  agent,
  'Explain AI agents.',
  {
    context: {},
  },
);

if (!result.success) {
  console.error(result.error.code);
  console.error(result.error.message);
}
```

Provider errors can expose whether they are retryable:

```ts
if (!result.success && result.error.retryable) {
  // Apply application-level retry policy.
}
```

Agni reports whether a failure is retryable.

The application controls the actual retry strategy.

---

# Runtime limits

The Runner supports execution limits configured on the Agent.

For example:

```ts
MAX_TURNS_EXCEEDED
```

When the maximum number of turns is exceeded, the Runner returns a failed `RunResult`.

Example:

```ts
const result = await runner.run(
  agent,
  'Perform a complex task.',
  {
    context: {},
  },
);

if (!result.success) {
  if (result.error.code === 'MAX_TURNS_EXCEEDED') {
    console.error(
      'Agent exceeded the maximum number of turns.',
    );
  }
}
```

# `stream()`

Streams model output incrementally.

Instead of waiting for the provider to return the complete response, `stream()` returns an async iterable of provider-agnostic Agni stream events.

```ts
const stream = runner.stream(
  agent,
  'Explain what an AI agent is.',
  {
    context: {},
  },
);

for await (const event of stream) {
  if (event.type === 'text_delta') {
    process.stdout.write(event.text);
  }
}
```

---

## Signature

```ts
stream(
  agent: Agent,
  input: string,
  options: RunOptions<TContext>,
): AsyncIterable<RunStreamEvent>;
```

---

## Parameters

| Parameter | Type                   | Required | Description                    |
| --------- | ---------------------- | -------- | ------------------------------ |
| `agent`   | `Agent`                | Yes      | Agent instance to execute      |
| `input`   | `string`               | Yes      | User input passed to the agent |
| `options` | `RunOptions<TContext>` | Yes      | Runtime execution options      |

---

# Stream events

`stream()` returns:

```ts
AsyncIterable<RunStreamEvent>
```

The public stream event type is:

```ts
type RunStreamEvent =
  | RunStreamTextEvent
  | RunStreamToolCallEvent
  | RunStreamDoneEvent;
```

Every public stream event contains a `runId`.

---

## Text events

Incremental model text is exposed as:

```ts
interface RunStreamTextEvent {
  type: 'text_delta';

  runId: string;

  text: string;
}
```

Example:

```ts
{
  type: 'text_delta',
  runId: 'df458eda-fdcd-4717-86ae-a24bc83ef86a',
  text: 'An AI agent perceives'
}
```

Applications can immediately render the text.

---

## Tool-call events

Agni also defines a normalized stream event for incremental tool-call information:

```ts
interface RunStreamToolCallEvent {
  type: 'tool_call_delta';

  runId: string;

  id?: string;

  name?: string;

  arguments?: string;
}
```

This allows provider adapters to expose provider-specific streamed tool-call information through a common contract.

The current Runner streaming loop does not execute streamed tool calls.

---

## Done events

When streaming completes, the Runner exposes:

```ts
interface RunStreamDoneEvent {
  type: 'done';

  runId: string;
}
```

Example:

```ts
for await (const event of runner.stream(
  agent,
  'Explain AI agents.',
  {
    context: {},
  },
)) {
  if (event.type === 'done') {
    console.log('Stream completed.');
  }
}
```

# Complete streaming example

```ts
import {
  Agent,
  GeminiProvider,
  Runner,
} from 'agni-agent-sdk';

const provider = new GeminiProvider({
  apiKey: process.env.GEMINI_API_KEY,
});

const agent = new Agent({
  name: 'stream-test',

  instructions:
    'You are a helpful assistant. Keep responses concise.',

  provider,
});

const runner = new Runner();

const stream = runner.stream(
  agent,

  'Explain what an AI agent is.',

  {
    context: {},
  },
);

for await (const event of stream) {
  if (event.type === 'text_delta') {
    process.stdout.write(event.text);
  }
}
```

The model response is displayed incrementally as text chunks arrive.

# Streaming architecture

The Runner sits between the provider's normalized stream and the application.

```text
Agent
  |
  v
RunContext
  |
  v
Provider.stream()
  |
  v
ModelStreamChunk
  |
  v
Runner
  |
  v
RunStreamEvent
  |
  v
Application
```

Providers are responsible for converting their native streaming responses into Agni's `ModelStreamChunk` types.

The Runner then converts those chunks into public `RunStreamEvent` values.

This keeps applications independent from provider SDKs.

# `run()` vs `stream()`

Use `run()` when you need the final normalized result:

```ts
const result = await runner.run(
  agent,
  input,
  {
    context: {},
  },
);
```

Use `stream()` when you need incremental model output:

```ts
for await (const event of runner.stream(
  agent,
  input,
  {
    context: {},
  },
)) {
  if (event.type === 'text_delta') {
    process.stdout.write(event.text);
  }
}
```

The execution models are:

```text
run()
  |
  v
Provider.generate()
  |
  v
ModelResponse
  |
  v
Tool Loop
  |
  v
RunResult
```

and:

```text
stream()
  |
  v
Provider.stream()
  |
  v
ModelStreamChunk
  |
  v
RunStreamEvent
  |
  v
Consumer
```

# Events

The Runner also publishes runtime lifecycle events through its `EventBus`.

Access the event bus through:

```ts
runner.events;
```

Example:

```ts
runner.events.on(
  'tool.called',
  (event) => {
    console.log(event.toolName);
  },
);
```

Current runtime events include:

| Event               | Description                            |
| ------------------- | -------------------------------------- |
| `agent.started`     | Agent execution started                |
| `turn.started`      | A new runtime turn started             |
| `provider.request`  | Request sent to the model provider     |
| `provider.response` | Provider returned a response           |
| `tool.called`       | Tool execution was requested           |
| `tool.completed`    | Tool execution completed               |
| `agent.completed`   | Agent execution completed successfully |

---

# EventBus vs `stream()`

These two APIs serve different purposes.

| EventBus              | `runner.stream()`        |
| --------------------- | ------------------------ |
| Runtime lifecycle     | Incremental model output |
| Observability         | Live response rendering  |
| Tool execution events | Text deltas              |
| Provider lifecycle    | Stream completion        |
| Logging               | Chat interfaces          |
| Metrics               | Interactive applications |

For example, runtime events can be observed through:

```ts
runner.events.on(
  'tool.called',
  (event) => {
    console.log('Tool:', event.toolName);
  },
);
```

While generated text can be consumed through:

```ts
for await (const event of runner.stream(
  agent,
  input,
  {
    context: {},
  },
)) {
  if (event.type === 'text_delta') {
    process.stdout.write(event.text);
  }
}
```

# Custom Event Bus

A custom event bus can be provided to the Runner:

```ts
const runner = new Runner(customEventBus);
```

This can be useful for integrating runtime events with:

* Logging
* Observability
* Monitoring
* Metrics
* Custom event pipelines

# Error handling

Expected failures from `run()` are returned as a failed `RunResult`.

```ts
const result = await runner.run(
  agent,
  'Explain AI agents.',
  {
    context: {},
  },
);

if (!result.success) {
  console.error({
    code: result.error.code,
    message: result.error.message,
    retryable: result.error.retryable,
    runId: result.metadata?.runId,
  });

  return;
}

console.log(result.output);
```

Streaming behaves differently.

Provider failures during `stream()` are surfaced through the async generator.

```ts
try {
  for await (const event of runner.stream(
    agent,
    input,
    {
      context: {},
    },
  )) {
    if (event.type === 'text_delta') {
      process.stdout.write(event.text);
    }
  }
} catch (error) {
  console.error(error);
}
```

The Runner normalizes provider failures into `ProviderError` before surfacing them.

---

# Run ID

Every Runner execution receives a unique run ID.

For normal execution, the ID is available through:

```ts
result.metadata?.runId;
```

For streaming, every public stream event contains the run ID:

```ts
event.runId;
```

This makes it possible to correlate:

* Runtime events
* Provider requests
* Tool execution
* Stream events
* Final results

Example:

```ts
for await (const event of runner.stream(
  agent,
  input,
  {
    context: {},
  },
)) {
  console.log(event.runId);
}
```
