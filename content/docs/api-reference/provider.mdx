# Provider

A Provider connects Agni's runtime with an AI model.

Providers are responsible for:

* Sending requests to AI models
* Translating Agni requests into provider-specific requests
* Normalizing provider responses
* Exposing provider and model metadata
* Normalizing provider failures into Agni errors

Agni keeps the runtime independent from provider-specific APIs.

This means the `Runner` does not need to know whether an agent uses Gemini, OpenAI, Anthropic, or a custom provider.

---

## Import

```ts
import type {
  ModelProvider,
  ProviderInfo,
} from 'agni-agent-sdk';
```

---

# Provider architecture

Agni uses a provider abstraction layer between the runtime and model APIs.

```text
Application
    |
    v
  Agent
    |
    v
  Runner
    |
    v
ModelProvider
    |
    +-------------------+
    |                   |
    v                   v
 Gemini              Custom
 Provider            Provider
    |                   |
    v                   v
 Gemini API          Model API
    |                   |
    +-------------------+
            |
            v
    Normalized Response
```

The runtime communicates with the `ModelProvider` interface rather than directly with a model SDK.

---

# ModelProvider

The provider contract is defined by `ModelProvider`.

```ts
interface ModelProvider {
  readonly info: ProviderInfo;

  generate(
    request: ModelRequest,
  ): Promise<ModelResponse>;
}
```

---

# ProviderInfo

Each provider exposes metadata describing the provider and configured model.

```ts
interface ProviderInfo {
  name: string;

  model: string;
}
```

Example:

```ts
provider.info;
```

Result:

```ts
{
  name: 'gemini',

  model: 'gemini-2.5-flash',
}
```

---

## `info.name`

Identifies the provider.

```ts
provider.info.name;
```

Example:

```ts
'gemini';
```

This metadata is also included in runtime provider events.

---

## `info.model`

Identifies the configured model.

```ts
provider.info.model;
```

Example:

```ts
'gemini-2.5-flash';
```

The Runner uses this information when emitting provider lifecycle events.

---

# `generate()`

The `generate()` method sends a normalized model request to the provider.

```ts
provider.generate(request);
```

The provider converts the request into the format required by the underlying model API.

---

# ModelRequest

Agni's runtime creates a normalized `ModelRequest`.

A request contains the conversation, available tools, and provider-specific options.

Example:

```ts
{
  messages,

  tools,

  providerOptions,
}
```

The exact request type is:

```ts
ModelRequest
```

The provider receives this normalized structure instead of receiving the `Agent` directly.

---

# Messages

The `messages` field contains the conversation history.

```ts
messages: Message[];
```

Messages can represent:

* System instructions
* User messages
* Assistant responses
* Tool calls
* Tool results

Example:

```ts
[
  {
    role: 'system',
    content: 'You are a helpful assistant.',
  },

  {
    role: 'user',
    content: 'What is the weather in Pune?',
  },
]
```

The provider adapter converts these messages into its native API format.

---

# Tools

The runtime passes registered tools to the provider.

```ts
tools: ProviderToolDefinition[];
```

A provider uses these definitions to expose available tools to the model.

Example:

```ts
[
  {
    name: 'get_weather',

    description: 'Returns the weather for a city.',

    parameters: {
      type: 'object',

      properties: {
        city: {
          type: 'string',
        },
      },

      required: ['city'],
    },
  },
]
```

The provider adapter is responsible for converting these definitions into the provider-specific tool format.

---

# Provider options

Provider-specific configuration can be passed through:

```ts
providerOptions;
```

This allows provider adapters to support provider-specific settings without coupling the core runtime to a particular model provider.

For example:

```ts
const agent = new Agent({
  name: 'assistant',

  provider,

  providerOptions: {
    temperature: 0.7,
  },
});
```

The exact supported options depend on the provider implementation.

---

# ModelResponse

Providers return a normalized `ModelResponse`.

Agni currently supports responses such as:

### Text response

```ts
{
  type: 'text',

  content: 'Hello, how can I help?',
}
```

### Tool call response

```ts
{
  type: 'tool_call',

  toolCalls: [
    {
      id: 'call_123',

      name: 'get_weather',

      arguments: {
        city: 'Pune',
      },
    },
  ],
}
```

The Runner uses the response type to determine the next step in the agent execution loop.

---

# Provider lifecycle

During an agent run, the provider participates in the following lifecycle:

```text
Runner
   |
   v
provider.request
   |
   v
ModelProvider.generate()
   |
   v
Provider Adapter
   |
   v
Model API
   |
   v
Provider Response
   |
   v
provider.response
   |
   v
Runner
```

The Runner emits provider events before and after the provider request.

---

# Runtime provider events

The Runner emits:

```ts
'provider.request'
```

before calling the provider.

Example event:

```ts
{
  type: 'provider.request',

  runId: 'run_123',

  timestamp: Date.now(),

  provider: 'gemini',

  model: 'gemini-2.5-flash',
}
```

After the provider responds, the Runner emits:

```ts
'provider.response'
```

Example:

```ts
{
  type: 'provider.response',

  runId: 'run_123',

  timestamp: Date.now(),

  provider: 'gemini',

  model: 'gemini-2.5-flash',
}
```

These events can be used for:

* Debugging
* Logging
* Observability
* Tracing
* Runtime monitoring

# Built-in providers

Agni currently provides a Gemini provider implementation.

## Gemini

```ts
import { GeminiProvider } from 'agni-agent-sdk';
```

Example:

```ts
const provider = new GeminiProvider({
  apiKey: process.env.GEMINI_API_KEY!,
});
```

The provider exposes its configured metadata through:

```ts
provider.info;
```

---

# Using a provider

Providers are passed into an `Agent`.

```ts
import {
  Agent,
  GeminiProvider,
} from 'agni-agent-sdk';

const provider = new GeminiProvider({
  apiKey: process.env.GEMINI_API_KEY!,
});

const agent = new Agent({
  name: 'assistant',

  instructions: 'You are a helpful assistant.',

  provider,
});
```

The same Agent/Runner architecture can work with another provider implementing `ModelProvider`.

---

# Custom providers

Agni's provider abstraction allows applications to implement custom providers.

Example:

```ts
import type {
  ModelProvider,
  ModelRequest,
  ModelResponse,
} from 'agni-agent-sdk';

class CustomProvider implements ModelProvider {
  readonly info = {
    name: 'custom-provider',
    model: 'custom-model',
  };

  async generate(
    request: ModelRequest,
  ): Promise<ModelResponse> {
    const response = await myModel.generate(request);

    return {
      type: 'text',

      content: response.text,
    };
  }
}
```

The custom provider only needs to satisfy Agni's normalized provider contract.

# Provider errors

Provider failures are normalized by the runtime into Agni provider errors.

The base error is:

```ts
ProviderError
```

Import it with:

```ts
import {
  ProviderError,
} from 'agni-agent-sdk';
```

Provider errors contain information such as:

```ts
error.code;

error.provider;

error.model;

error.metadata;

error.retryable;
```

---

# Provider error types

Agni currently defines the following provider errors:

| Error                         | Code                            | Retryable        |
| ----------------------------- | ------------------------------- | ---------------- |
| `ProviderError`               | `PROVIDER_ERROR`                | Depends on error |
| `ProviderAuthenticationError` | `PROVIDER_AUTHENTICATION_ERROR` | No               |
| `ProviderRateLimitError`      | `PROVIDER_RATE_LIMIT_ERROR`     | Yes              |
| `ProviderTimeoutError`        | `PROVIDER_TIMEOUT_ERROR`        | Yes              |
| `ProviderResponseError`       | `PROVIDER_RESPONSE_ERROR`       | No               |

---

## ProviderAuthenticationError

Used when provider authentication fails.

Common causes:

* Invalid API key
* Expired credentials
* Invalid authentication configuration

Example:

```ts
if (!result.success) {
  if (
    result.error.code ===
    'PROVIDER_AUTHENTICATION_ERROR'
  ) {
    console.error('Check provider credentials.');
  }
}
```

Authentication errors are not retryable by default.

---

## ProviderRateLimitError

Used when the provider rejects a request because of rate limits or quota.

```ts
ProviderRateLimitError
```

Error code:

```ts
'PROVIDER_RATE_LIMIT_ERROR'
```

This error is marked as retryable.

Applications can use this information to implement retry or backoff strategies.

---

## ProviderTimeoutError

Used when a provider request exceeds the configured or provider-side timeout.

```ts
ProviderTimeoutError
```

Error code:

```ts
'PROVIDER_TIMEOUT_ERROR'
```

This error is marked as retryable.

---

## ProviderResponseError

Used when the provider returns an invalid or malformed response.

```ts
ProviderResponseError
```

Error code:

```ts
'PROVIDER_RESPONSE_ERROR'
```

This error is not retryable by default.

---

# Handling provider failures

Provider failures are returned through `RunResult`.

```ts
const result = await runner.run(
  agent,

  'Explain AI agents.',

  {
    context: {},
  },
);

if (!result.success) {
  console.error({
    code: result.error.code,

    message: result.error.message,

    retryable: result.error.retryable,

    runId: result.metadata?.runId,
  });
}
```

This allows applications to handle failures without depending on provider-specific error objects.

---

# Retryable errors

Provider errors expose a `retryable` property.

```ts
result.error.retryable;
```

Example:

```ts
if (
  !result.success &&
  result.error.retryable
) {
  // Retry according to application policy.
}
```

Typical retryable provider failures include:

* Rate limits
* Timeouts

Authentication and malformed-response errors are not retryable by default.

---

# Provider independence

The main advantage of the provider abstraction is that the runtime does not depend on a specific model provider.

```text
                  Agent
                    |
                    v
                  Runner
                    |
                    v
             ModelProvider
                    |
        +-----------+-----------+
        |           |           |
        v           v           v
      Gemini     OpenAI      Custom
```

The Agent and Runner can remain unchanged while the provider implementation changes.
