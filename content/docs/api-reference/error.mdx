# Error

Agni uses a structured error system to make agent failures predictable, debuggable, and machine-readable.

The error system currently covers:

* Base Agni errors
* Provider errors
* Tool errors
* Validation errors
* Guardrail errors
* Configuration errors
* Runtime execution limits

Agni separates **internal error objects** from the **serializable errors returned through `RunResult`**.

# Error architecture

All Agni runtime errors extend the base `AgniError` class.

```text
AgniError
│
├── ProviderError
│   ├── ProviderAuthenticationError
│   ├── ProviderRateLimitError
│   ├── ProviderTimeoutError
│   └── ProviderResponseError
│
├── ToolNotFoundError
├── ToolExecutionError
├── ToolValidationError
├── ToolRegistrationError
│
├── ValidationError
│   ├── AgentValidationError
│   └── RunValidationError
│
├── GuardrailError
│   ├── InputGuardrailError
│   ├── ToolGuardrailError
│   └── OutputGuardrailError
│
└── ConfigurationError
    ├── MissingConfigurationError
    └── InvalidConfigurationError
```

This hierarchy allows applications to handle errors at different levels of specificity.

For example:

```ts
if (error instanceof ProviderError) {
  // Handle all provider failures
}
```

or:

```ts
if (error instanceof ProviderRateLimitError) {
  // Handle rate limiting specifically
}
```

# AgniError

`AgniError` is the base error class for the Agni runtime.

```ts
class AgniError extends Error {
  readonly code: string;
  readonly metadata?: Record<string, unknown>;
  readonly cause?: unknown;
  readonly retryable: boolean;
}
```

Every Agni-specific error inherits these properties.

---

## `code`

A stable machine-readable identifier for the error.

```ts
error.code;
```

Example:

```ts
'PROVIDER_RATE_LIMIT_ERROR';
```

Error codes should be used for:

* Conditional handling
* Logging
* Monitoring
* Analytics
* Retry decisions

Do not rely on the human-readable error message for program logic.

---

## `metadata`

Optional debugging and contextual information.

```ts
error.metadata;
```

Example:

```ts
{
  provider: 'gemini',
  model: 'gemini-2.5-flash'
}
```

Metadata is intended to provide additional context without changing the stable error code.

---

## `cause`

The original underlying error, when available.

```ts
error.cause;
```

This is useful when Agni wraps an error thrown by a provider, tool, or another runtime component.

Example:

```ts
try {
  // provider operation
} catch (error) {
  throw new ProviderError('Provider request failed.', {
    cause: error,
  });
}
```

---

## `retryable`

Indicates whether retrying the operation may succeed.

```ts
error.retryable;
```

Example:

```ts
if (error.retryable) {
  // Retry according to your application's policy
}
```

Agni marks errors such as provider rate limits and provider timeouts as retryable.

---

# Provider errors

Provider errors represent failures originating from an AI model provider.

The base class is:

```ts
ProviderError
```

Provider errors contain optional provider and model information.

```ts
const error = new ProviderError(
  'Provider request failed.',
  {
    provider: 'gemini',
    model: 'gemini-2.5-flash',
  },
);
```

---

## ProviderAuthenticationError

Used when provider authentication fails.

Common causes:

* Invalid API key
* Expired credentials
* Missing credentials
* Invalid authentication configuration

```ts
new ProviderAuthenticationError(
  'Provider authentication failed.',
  {
    provider: 'gemini',
  },
);
```

Code:

```text
PROVIDER_AUTHENTICATION_ERROR
```

This error is **not retryable** by default.

---

## ProviderRateLimitError

Used when a provider rejects a request because a rate limit has been reached.

```ts
new ProviderRateLimitError(
  'Provider rate limit exceeded.',
  {
    provider: 'gemini',
    retryAfter: 30,
  },
);
```

Code:

```text
PROVIDER_RATE_LIMIT_ERROR
```

This error is marked as **retryable**.

The optional `retryAfter` value can be used by an application-level retry strategy.

---

## ProviderTimeoutError

Used when a provider request exceeds its allowed execution time.

```ts
new ProviderTimeoutError(
  'Provider request timed out.',
  {
    provider: 'gemini',
  },
);
```

Code:

```text
PROVIDER_TIMEOUT_ERROR
```

This error is marked as **retryable**.

---

## ProviderResponseError

Used when the provider returns an invalid or malformed response.

```ts
new ProviderResponseError(
  'Invalid provider response.',
  {
    provider: 'gemini',
  },
);
```

Code:

```text
PROVIDER_RESPONSE_ERROR
```

This error is not retryable by default.

---

# Tool errors

Tool errors represent failures involving agent tools.

---

## ToolNotFoundError

Thrown when the runtime attempts to execute a tool that is not registered.

```ts
new ToolNotFoundError('get_weather');
```

Code:

```text
TOOL_NOT_FOUND
```

The error metadata contains the tool name:

```ts
{
  toolName: 'get_weather'
}
```

---

## ToolExecutionError

Represents a failure while executing tool logic.

```ts
new ToolExecutionError(
  'Weather API request failed.',
  {
    toolName: 'get_weather',
  },
  originalError,
);
```

Code:

```text
TOOL_EXECUTION_ERROR
```

The original error can be accessed through:

```ts
error.cause;
```

---

## ToolValidationError

Used when tool input validation fails.

```ts
new ToolValidationError(
  'Invalid tool input.',
  {
    toolName: 'get_weather',
  },
);
```

Code:

```text
TOOL_VALIDATION_ERROR
```

---

## ToolRegistrationError

Used when a tool cannot be registered correctly.

For example, registering the same tool name twice:

```ts
registry.register(weatherTool);

registry.register(weatherTool);
```

The second registration results in:

```text
TOOL_REGISTRATION_ERROR
```

Example metadata:

```ts
{
  toolName: 'get_weather'
}
```

---

# Validation errors

Validation errors represent invalid input or runtime configuration.

The base class is:

```ts
ValidationError
```

## AgentValidationError

Examples include:

```ts
new AgentValidationError(
  'Invalid agent configuration.',
);
```

Code:

```text
VALIDATION_ERROR
```

---

## RunValidationError

Used when runtime execution input is invalid.

Examples include:

* Invalid run input
* Invalid runtime options
* Invalid run context

```ts
new RunValidationError(
  'Invalid run configuration.',
);
```

Code:

```text
VALIDATION_ERROR
```

# Guardrail errors

Guardrail errors represent execution being rejected by a configured safety or policy guardrail.

The base class is:

```ts
GuardrailError
```

Guardrail failures are **not retryable** by default.

---

## InputGuardrailError

Used when user or agent input is rejected.

Examples:

* Unsafe input
* Policy violation
* Blocked content

```ts
new InputGuardrailError(
  'Input was rejected by the configured guardrail.',
);
```

Code:

```text
GUARDRAIL_ERROR
```

---

## ToolGuardrailError

Used when a tool execution is rejected by a tool guardrail.

This error contains information about both the tool and the guardrail.

```ts
new ToolGuardrailError(
  'Tool execution was blocked.',
  {
    toolName: 'delete_file',
    guardrailName: 'protected-files',
  },
);
```

The error exposes:

```ts
error.toolName;
error.guardrailName;
```

Example:

```ts
console.log(error.toolName);
// delete_file

console.log(error.guardrailName);
// protected-files
```

Code:

```text
GUARDRAIL_ERROR
```

---

## OutputGuardrailError

Used when generated agent output is rejected by an output guardrail.

Examples:

* Output policy violation
* Unsafe generated content
* Restricted output

```ts
new OutputGuardrailError(
  'Agent output was rejected by the configured guardrail.',
);
```

Code:

```text
GUARDRAIL_ERROR
```

---

Configuration errors represent invalid or incomplete Agni configuration.

The base class is:

```ts
ConfigurationError
```

---

## MissingConfigurationError

Used when required configuration is missing.

Examples:

* Missing API key
* Missing provider configuration

```ts
new MissingConfigurationError(
  'Gemini API key is missing.',
);
```

Code:

```text
CONFIGURATION_ERROR
```

---

## InvalidConfigurationError

Used when a configuration value is present but invalid.

Examples:

* Invalid model name
* Invalid timeout

```ts
new InvalidConfigurationError(
  'Invalid model configuration.',
);
```

Code:

```text
CONFIGURATION_ERROR
```

# RunResult errors

`Runner.run()` returns a structured `RunResult`.

Expected runtime failures are represented as:

```ts
{
  success: false,

  error: {
    code: 'PROVIDER_ERROR',
    message: 'Provider request failed.',
    metadata: {},
    retryable: false,
  },

  metadata: {
    runId: 'run_123',
    turns: 2,
  },
}
```

The `error` returned in `RunResult` is intentionally serializable.

The internal `AgniError` instance contains richer information such as:

```ts
error.cause;
```

but the public `RunResult.error` contains the structured information required by applications.

---

# Error codes

The runtime currently defines these error codes:

| Code                            | Description                                 |
| ------------------------------- | ------------------------------------------- |
| `AGNI_ERROR`                    | Base Agni error                             |
| `PROVIDER_ERROR`                | General provider failure                    |
| `PROVIDER_AUTHENTICATION_ERROR` | Provider authentication failed              |
| `PROVIDER_RATE_LIMIT_ERROR`     | Provider rate limit exceeded                |
| `PROVIDER_TIMEOUT_ERROR`        | Provider request timed out                  |
| `PROVIDER_RESPONSE_ERROR`       | Provider returned an invalid response       |
| `TOOL_NOT_FOUND`                | Requested tool is not registered            |
| `TOOL_EXECUTION_ERROR`          | Tool execution failed                       |
| `TOOL_VALIDATION_ERROR`         | Tool input validation failed                |
| `TOOL_REGISTRATION_ERROR`       | Tool registration failed                    |
| `VALIDATION_ERROR`              | Runtime validation failed                   |
| `GUARDRAIL_ERROR`               | Execution was rejected by a guardrail       |
| `CANCELLED`                     | Execution was cancelled                     |
| `MAX_TURNS_EXCEEDED`            | Agent exceeded the configured maximum turns |

---

# Handling errors

The recommended approach is to check `success` before accessing the result.

```ts
const result = await runner.run(
  agent,
  'Explain AI agents',
  {
    context: {},
  },
);

if (!result.success) {
  console.error(result.error);

  return;
}

console.log(result.output);
```

Because `RunResult` is a discriminated union, TypeScript automatically narrows the result.

---

# Handling by error code

Use the stable error code when the application needs specific behavior.

```ts
if (!result.success) {
  switch (result.error.code) {
    case 'PROVIDER_RATE_LIMIT_ERROR':
      // Retry with backoff
      break;

    case 'PROVIDER_TIMEOUT_ERROR':
      // Retry the request
      break;

    case 'TOOL_NOT_FOUND':
      // Investigate tool registration
      break;

    case 'GUARDRAIL_ERROR':
      // Do not retry automatically
      break;

    case 'MAX_TURNS_EXCEEDED':
      // Agent execution exceeded its limit
      break;
  }
}
```

---

# Retryable errors

Agni exposes a `retryable` property to help applications make retry decisions.

```ts
if (!result.success && result.error.retryable) {
  // Apply application-level retry policy
}
```

Currently, provider rate-limit and provider-timeout errors are marked as retryable.

Applications should still apply their own retry policy, including:

* Maximum retry attempts
* Exponential backoff
* Jitter
* Request budgets
* Idempotency considerations

---

# Production error handling

A production application should log the structured error rather than relying only on the message.

```ts
const result = await runner.run(agent, input, {
  context: {},
});

if (!result.success) {
  logger.error({
    code: result.error.code,
    message: result.error.message,
    metadata: result.error.metadata,
    retryable: result.error.retryable,
    runId: result.metadata?.runId,
    turns: result.metadata?.turns,
  });

  return;
}

return result.output;
```

The `runId` is particularly useful for connecting the error with runtime events.

# Debugging workflow

When an agent execution fails, use the following workflow:

```text
RunResult
   |
   v
Check error.code
   |
   v
Check retryable
   |
   v
Inspect error.metadata
   |
   v
Find runId
   |
   v
Inspect runtime events
```

For example:

```ts
if (!result.success) {
  console.log('Error:', result.error.code);
  console.log('Retryable:', result.error.retryable);
  console.log('Run ID:', result.metadata?.runId);
}
```

This gives the application enough information to understand what failed without depending on fragile error-message strings.
