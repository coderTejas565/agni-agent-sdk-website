# Tool

A `Tool` allows an Agni agent to interact with external systems and execute custom application logic.

Tools enable agents to perform actions such as:

* Calling APIs
* Querying databases
* Reading files
* Executing business logic
* Accessing application services

A tool contains:

* Metadata exposed to the model
* An input parameter schema
* Execution logic
* Access to the current `RunContext`

---

## Import

```ts
import type { Tool } from 'agni-agent-sdk';
```

---

# Tool architecture

During execution, Agni manages the complete tool lifecycle.

```text
User Input
    |
    v
  Runner
    |
    v
 Provider
    |
    v
Tool Selection
    |
    v
ToolGuardrail
    |
    | allowed
    v
ToolExecutor
    |
    v
   Tool
 execute()
    |
    v
Tool Result
    |
    v
ToolGuardrail
    |
    v
 Provider
    |
    v
Final Response
```

The model decides **when** a tool is required.

The Agni runtime controls **how** the tool executes.

---

# Type Definition

```ts
interface Tool<
  TContext = unknown,
  TInput = unknown,
  TOutput = unknown,
> {
  name: string;

  description: string;

  parameters: unknown;

  execute(
    input: TInput,
    context: RunContext<TContext>,
  ): TOutput | Promise<TOutput>;
}
```

---

# Properties

## `name`

Unique identifier used by the model to call the tool.

```ts
tool.name;
```

**Type**

```ts
string;
```

Example:

```ts
'get_weather';
```

The name should be:

* Unique
* Descriptive
* Stable

---

## `description`

Explains what the tool does.

```ts
tool.description;
```

**Type**

```ts
string;
```

The description is exposed to the model and helps it decide when the tool should be used.

Example:

```ts
description: 'Returns the current weather for a city.';
```

A clear description improves tool selection.

---

## `parameters`

Defines the input schema exposed to the model.

```ts
tool.parameters;
```

**Type**

```ts
unknown;
```

The runtime keeps the schema provider-agnostic. Provider adapters convert it into the format required by the model provider.

Example:

```ts
{
  type: 'object',

  properties: {
    city: {
      type: 'string',
      description: 'City name',
    },
  },

  required: ['city'],
}
```

---

## `execute()`

The function called when the runtime executes the tool.

```ts
tool.execute(input, context);
```

**Type**

```ts
(
  input: TInput,
  context: RunContext<TContext>,
) => TOutput | Promise<TOutput>;
```

The tool receives two arguments:

| Argument  | Description                      |
| --------- | -------------------------------- |
| `input`   | Arguments generated for the tool |
| `context` | Current Agni execution context   |

The returned value becomes the tool result available to the agent.

---

# Creating a tool

Example:

```ts
import type { Tool } from 'agni-agent-sdk';

export const weatherTool: Tool = {
  name: 'get_weather',

  description: 'Returns the weather for a city.',

  parameters: {
    type: 'object',

    properties: {
      city: {
        type: 'string',
        description: 'City name',
      },
    },

    required: ['city'],
  },

  async execute(input, context) {
    const { city } = input as { city: string };

    return {
      city,
      temperature: 29,
      condition: 'Sunny',
    };
  },
};
```

---

# Registering tools

Tools are provided when creating an Agent.

```ts
const agent = new Agent({
  name: 'weather-agent',

  instructions: 'Use weather tools when required.',

  provider,

  tools: [weatherTool],
});
```

The `Runner` registers the agent's tools with its internal `ToolRegistry`.

---

# Tool Registry

Agni uses `ToolRegistry` to manage tools during execution.

```ts
import { ToolRegistry } from 'agni-agent-sdk';
```

The registry is responsible for:

* Registering tools
* Looking up tools by name
* Checking whether a tool exists
* Removing tools
* Generating provider tool definitions

The registry does **not** execute tools.

Tool execution belongs to `ToolExecutor`.

---

# Tool execution

`ToolExecutor` is responsible for executing a registered tool.

```text
Provider
    |
    v
Tool Call
    |
    v
ToolRegistry
    |
    v
ToolExecutor
    |
    v
Tool
```

The executor:

1. Resolves the tool from the registry.
2. Passes the input and `RunContext` to the tool.
3. Executes the tool.
4. Normalizes execution failures.
5. Returns a structured execution result.

---

# Tool execution result

The executor returns a discriminated union.

### Successful execution

```ts
{
  success: true,

  output: result,
}
```

### Failed execution

```ts
{
  success: false,

  error: Error,
}
```

This allows the runtime to handle tool failures without relying on exceptions for normal control flow.

---

# Tool Guardrails

Agni supports guardrails around tool execution.

A tool guardrail can inspect a tool call **before execution** and its result **after execution**.

```ts
interface ToolGuardrail<TContext = unknown> {
  name: string;

  beforeExecute?(
    toolName: string,
    input: unknown,
    context: RunContext<TContext>,
  ): ToolGuardrailResult | Promise<ToolGuardrailResult>;

  afterExecute?(
    toolName: string,
    output: unknown,
    context: RunContext<TContext>,
  ): ToolGuardrailResult | Promise<ToolGuardrailResult>;
}
```

A guardrail returns:

```ts
interface ToolGuardrailResult {
  allowed: boolean;

  reason?: string;
}
```

---

# Guardrail execution flow

The intended tool execution flow is:

```text
Tool Call
    |
    v
beforeExecute()
    |
    +---- allowed ----> ToolExecutor
    |                       |
    |                       v
    |                   tool.execute()
    |                       |
    |                       v
    |                  afterExecute()
    |                       |
    |                       v
    |                   Tool Result
    |
    +---- blocked ----> ToolGuardrailError
```

This allows applications to enforce policies before a tool is executed and inspect the result afterward.

---

# ToolGuardrailError

When a tool execution is rejected by a guardrail, Agni represents the failure using `ToolGuardrailError`.

```ts
import { ToolGuardrailError } from 'agni-agent-sdk';
```

`ToolGuardrailError` extends `GuardrailError`, which extends `AgniError`.

It contains:

```ts
error.toolName;
error.guardrailName;
error.code;
error.message;
error.metadata;
error.retryable;
```

The error code is:

```ts
'GUARDRAIL_ERROR';
```

Example:

```ts
throw new ToolGuardrailError(
  'Tool execution was blocked by policy.',
  {
    toolName: 'delete_account',
    guardrailName: 'destructive-action-policy',
  },
);
```

---

# Handling tool guardrail failures

Guardrail failures are returned through `RunResult`.

```ts
const result = await runner.run(
  agent,

  'Delete my account',

  {
    context: {},
  },
);

if (!result.success) {
  console.log(result.error.code);
}
```

A guardrail-blocked failure can be identified from the error code and metadata.

```ts
if (!result.success) {
  if (result.error.code === 'GUARDRAIL_ERROR') {
    console.log('Tool execution was blocked.');
  }
}
```

---

# Tool errors

Tool execution failures are normalized by `ToolExecutor`.

For example:

```ts
const databaseTool: Tool = {
  name: 'get_user',

  description: 'Fetches a user from the database.',

  parameters: {
    type: 'object',

    properties: {
      userId: {
        type: 'string',
      },
    },

    required: ['userId'],
  },

  async execute() {
    throw new Error('Database unavailable');
  },
};
```

The runtime converts unexpected tool failures into:

```ts
ToolExecutionError
```

with the error code:

```ts
'TOOL_EXECUTION_ERROR';
```

---

# Tool not found

If the model requests a tool that is not registered, `ToolExecutor` returns a `ToolNotFoundError`.

```ts
ToolNotFoundError
```

with the error code:

```ts
'TOOL_NOT_FOUND';
```

Example:

```ts
{
  success: false,

  error: {
    code: 'TOOL_NOT_FOUND',
    message: 'Tool "get_weather" not found.',
  },
}
```

---

# Accessing RunContext

Tools receive the current execution context.

Example:

```ts
const profileTool: Tool = {
  name: 'get_profile',

  description: 'Returns the current user profile.',

  parameters: {
    type: 'object',

    properties: {},
  },

  async execute(_input, context) {
    const userId = context.context.userId;

    return {
      userId,
    };
  },
};
```

`RunContext` allows tools to access application-specific runtime information without coupling the tool to the Runner.

---

# Tool execution lifecycle

When a model requests a tool, the runtime follows this flow:

```text
1. Provider requests a tool
        |
        v
2. Runner receives the tool call
        |
        v
3. Tool is resolved from ToolRegistry
        |
        v
4. Tool guardrail checks the request
        |
        +---- blocked ----> ToolGuardrailError
        |
        v
5. ToolExecutor executes the tool
        |
        +---- failed ----> ToolExecutionError
        |
        v
6. Post-execution guardrail checks result
        |
        +---- blocked ----> ToolGuardrailError
        |
        v
7. Tool result added to conversation
        |
        v
8. Provider generates next response
```

# Best practices

## Keep tools focused

Good:

```text
get_weather(city)
```

Avoid:

```text
do_everything()
```

A focused tool is easier for the model to understand and safer to execute.

---

## Return structured data

Prefer:

```json
{
  "temperature": 29,
  "condition": "Sunny"
}
```

Instead of:

```text
"The temperature is 29 degrees."
```

Structured outputs make tool results easier for the model and application code to consume.

---

## Write clear descriptions

The model uses tool descriptions when deciding which tool to call.

Good:

```text
Searches customer orders by email address.
```

Poor:

```text
Search tool.
```

---

## Protect sensitive operations

Use guardrails for operations that can:

* Delete data
* Modify accounts
* Make financial changes
* Send external messages
* Trigger irreversible actions

For example:

```text
Model
  |
  v
delete_account
  |
  v
Destructive Action Guardrail
  |
  +---- blocked
  |
  +---- allowed
         |
         v
    Execute Tool
```
